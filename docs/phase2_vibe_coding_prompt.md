# Phase 2 AI-assisted implementation prompt

This is the consolidated build prompt/specification used to guide the Phase 2 implementation in this working copy. Keep a copy of the exact prompt/session you personally used for your course evaluation if the professor asks for the original interaction history; do not claim that this written specification is a screenshot or transcript of a different session.

> Extend the existing Asali/Nakali Part A project in place while preserving the five independent MySQL sources, mediator API, source SQL views, current Part A GUI, and two-computer deployment. Add a Phase 2 workflow for noisy medicine-label data. Use local Tesseract OCR through pytesseract and Pillow to extract raw text from uploaded images; retain raw OCR output and expose extracted item code, product name, batch number, manufacturer, and expiry date for review. Implement bidirectional entity matching: noisy observation to canonical medicine candidates and canonical medicine to approximately matching scan observations. Read canonical candidates and observations from live MySQL records on every request; do not hardcode the catalogue or cache it between requests. Combine conservative identifier normalization/OCR-confusion handling, edit-distance similarity, and weighted contextual similarity. Treat conflicting known batch/expiry data as a reason to prevent automatic correction, distinguish automatic matches from review/no-match outcomes, and explain candidate scores. Add an additive Phase 2 resolution table that preserves the raw observation and stores an optional canonical code, score, status, reason, human approval flag, and timestamps. Do not drop or modify Part A tables during the Phase 2 migration. Add API endpoints for matching, saving an auditable resolution, viewing saved resolutions, and reverse matching; add a Streamlit tab for the workflow. Correct Part A decision logic so a failed/missing authority report is not treated as proof of ASALI. Add unit tests, a labelled synthetic evaluation comparing exact/fuzzy/hybrid baselines, migration/permission instructions, and documentation. Use parameterized SQL for values and only grant the integration user the minimum permissions needed for the new resolution table. Clearly document that scores/thresholds are initial settings and avoid claiming universal accuracy from the small synthetic test set. Run syntax checks and tests before packaging.
